## Plan edits proposed (from the corpus)

1. **C2 confirmed, concrete form (PLAN 3.2).** `TpeResponse::reauthorize` with the fixed placeholder
   action fails for every conditional shape with `InconsistentRequests(InconsistentAction)`
   (`shapes::placeholder_action_breaks_reauthorize_c2`, 17 requests). The plain `Authorizer` path with
   the placeholder action is correct. So `Consistent` in Lean must be defined action-independently
   (as the plan already proposes) and the Lean `reauthorize` theorems cannot be applied with a
   different action; add the lemma `residual_independent_of_action` as an explicit bridge. Also note:
   `reauthorize` performs the consistency check that the plain path does not (stored present although
   TPE said `absent` is an `Err`, `risks::r7_*`); evaluateConditions has no such check, which is a
   trusted-gap line item (T-5).
2. **Action entities (D-13).** Do not put action entities in the `Entities` JSON, in either phase:
   `Entities::from_json_value`/`PartialEntities::from_json_value` reject them
   (`entity k8s::Action::"create" has type k8s::Action which is not declared`). The schema supplies
   them, and `action in k8s::Action::"update"` / `"delete"` then matches `patch` / `deletecollection`
   (shapes `patch-*`, `deletecollection-*`). Without `"patch" in ["update"]` the patch shape becomes
   NoOpinion (mutation test).
3. **Name source (3.2, review B I4), two additions.** (a) Create without subresource: name is
   `object.metadata.name`; `AdmissionRequest.name` is empty (mutation test proves the shape needs it).
   (b) If the object carries only `generateName` (name not yet generated when admission runs), the
   name is absent and name policies do not apply (NoOpinion). **Not verified against the Go
   admission order**; stage 3 must pin whether validating admission sees the generated name.
4. **Phase-2 resource type comes from `requestResource` + `requestSubResource`**, not from `kind`:
   for `serviceaccounts/token` the kind group is `authentication.k8s.io` while the resource group is
   `""`. The object's `apiVersion` must equal `requestKind` (group/version) or phase 2 fails closed
   (multi-version CRD shape; mutation test).
5. **Schema shape (1.3).** `request`/`stored` optional records per (resource, subresource); subresource
   action types (`PodExec`, `ServiceAccountToken`) declare no `stored`. `namespace` is stated only when
   non-empty (cluster-wide deletecollection leaves it unstated = unknown; stating `absent` would be
   tighter). Principal `uid`/`extra` are not modelled in the spike; the principal id is `uid` or
   `sha256(username)` and principal type comes from the username prefix, as planned.
6. **Association (R-10 / stage 3).** TPE simplifies `A && (false && error)` but not `(A && false) &&
   error`. The Lean policy ASTs in stage 3 must be built left-nested like Cedar's text parser, or
   Lean and Rust residuals differ structurally (found while writing `R10.lean`).
7. **R-9 decision (PLAN 1.3 last bullet).** Results of `r9::*` at the pin:
   - A, record with declared keys: `labels["owner"]` type-checks (behind a `has` guard) and residuals
     work, but an object with any other label key fails entity validation, so the converter must drop
     undeclared keys (it does), and a policy on an undeclared key is accepted by the validator yet
     can never be true. Observed oddity: the residual for an undeclared key keeps only the `has`
     test (the equality conjunct is dropped); harmless under conformance, worth an upstream question.
   - B, open record (`additionalAttributes`): **rejected** at the pin
     (`UnsupportedFeature(OpenRecordsAndEntities)`). Not an option.
   - C, `Set<{key, value}>`: every object conforms (availability 100%), `labels.contains({key:"owner",
     value: principal.name})` decides correctly in TPE and phase 2, but policies lose the
     `labels["owner"]` syntax.
   - Recommendation: generate A for keys that appear in loaded policies (with undeclared keys dropped
     by the converter) and C as the fallback for maps no policy references by key; or C everywhere if
     policy ergonomics are acceptable. Decision for stage 3 / schema generator.
8. **R-6 / D-10** stays as written; add that `has_error_node` detection must check both
   `Policy::to_json` output (`{"error":[]}`) and `Policy::from_json` success, as `engine.rs` does.

## Lints (R-9, R-11, D-11, T-6): `spike/src/lint.rs`

- `has_guard_lint`: validates each policy alone; one bad policy is isolated (TPE over the whole set fails
  with a single unguarded access: `risks::has_guard_lint_isolates_the_bad_policy`).
- `forbid_can_error` (R-11 list): arithmetic `+ - *`, negation, extension calls (`decimal`, `ip`, ...),
  `getTag`. The KEP forbids and the 11 shipped policies are not flagged.
- `reserved_uid_lint`: rejects `resource ==`/`in` scopes, `resource ==` comparisons and entity literals
  with the reserved uid; `residual_mentions_action` confirms no corpus residual mentions `action`.
