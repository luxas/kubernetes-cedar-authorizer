## Findings

### Critical

**C1. TPE `Deny` with residual forbids is turned into an unconditional NoOpinion (breaks C-2 and L5).**
Evidence: PLAN 3.2 "If `decision.isSome` ... Cedar `deny` with no satisfied forbid -> `NoOpinion`". Cedar `decide()` (cedar-policy-core/src/tpe/response.rs:89-111) returns `Some(Deny)` for `(true_forbid=false, true_permit=false, residual_permit=false, residual_forbid=*)`, i.e. when no permit can fire, **even if residual forbids remain undecided**. In that case `full a d` is `Deny` when the forbid turns out true and `NoOpinion` otherwise. Returning NoOpinion lets a later authorizer (RBAC) allow a request that the forbid would deny: fail-open relative to full semantics. KEP "Authorizer requirements" (kep:3523ff) requires the ordering Deny (unconditional) > Deny (conditional) > NoOpinion (unconditional); a conditional Deny must not be pruned.
Why it matters: C-2 `decisive_means_exact` and L5 are false as stated; a proof attempt will fail, or worse the Rust code ships the fail-open.
Edit (PLAN 3.2, replace the first bullet of `conditionsAwareAuthorize`): "Run `Cedar.TPE.isAuthorized`. Do not use `decision` directly. Let F = residual forbids that are neither `false` nor `error`, P = residual permits that are neither `false` nor `error`, TF/TP = forbids/permits that are exactly `true`. If TF != {} -> `Deny` (unconditional). Else if F = {} and TP != {} -> `Allow`. Else if F = {} and P = {} -> `NoOpinion`. Otherwise emit a `ConditionsMap` with one Deny condition per member of F and one Allow condition per member of P union TP (a `true` permit becomes an Allow condition whose body is `true`). If P union TP = {} and F != {} the map has only Deny conditions: this is intended (conditional Deny must survive; KEP authorizer requirements, strength ordering)." Add theorem C-2': "`ofTpe` equals `full` whenever it is unconditional" with the case split above, and drop the sentence "`decision.isSome` => return the unconditional decision".

**C2. `Consistent a d` is unsatisfiable for several write shapes because the action is part of Cedar's request refinement.**
Evidence: PLAN 3.2 defines `Consistent a d :≡ RequestAndEntitiesRefine (dataToConcrete d) (attrsToPartial a)`. Cedar's `PartialRequest.action` is concrete (risk report Q1: "`action` (concrete)"), so the concrete action must equal the authorization-time action. But `d` is the AdmissionRequest (kep:2339-2352): it carries `operation` (CREATE/UPDATE/DELETE/CONNECT), not the verb. Mismatches required by the KEP: `patch` -> UPDATE, `update` -> CREATE (update-to-create, kep:3219-3232), `deletecollection` -> DELETE per object (kep:3451-3460, "the condition is written just as for `verb=delete`"), connect `create pods/exec` -> `CONNECT` with `object = PodExecOptions`, `oldObject = null` (kep:3195-3200). Also unspecified: the plan's table gives `deletecollection` the same action handling as `delete` yet KEP says policies for `delete` apply to `deletecollection`; with a scope `action == k8s::Action::"delete"` a `deletecollection` request is pruned at authorization time and NoOpinion is returned (contradicting the KEP), while with distinct actions the plan never says how policy authors reach both. Residual policies are scope-less `when` clauses (residual.rs:68-76 `from_when_clause_annos`), so action does not matter for *evaluation* in phase 2, only for the *proof relation* and for pruning in phase 1.
Edit (PLAN 1.3, add after the table; and 3.2): "Action mapping. The authorization-time action is the request verb. `deletecollection` is modelled as a member of the action group `delete` (`action in k8s::Action::"delete"` matches both) so one policy covers per-object admission. `patch` is a member of `update`. Phase 2 does not reconstruct the action from `operation`; `Consistent` is defined as `RequestRefines'` that ignores the action (Cedar's residuals are scope-less, see residual.rs:68), and the Lean statement carries the action in the *decision* (`Decision = f(residuals)`), not in `Data`. `dataToConcrete` takes the action from a fixed constant `phase2_action`, and a lemma `residual_independent_of_action` states that residual bodies mention no `action` variable (a load-time check: reject residuals with `Var::Action`)." Add the full operation table: verb -> op(s): create->CREATE|CONNECT(POST on connect); update->UPDATE|CREATE; patch->UPDATE|CREATE; delete->DELETE; deletecollection->DELETE (n times). Add `oldObject`/`object` presence per op to 1.3.

**C3. Entity ids in the existing code are random, and maps are entities; residual literals are not resolvable in phase 2.**
Evidence: `src/cedar_authorizer/entitybuilder.rs:22-32,60-73` (`new_uuid()` random; `build_unknown` uses `new_uuid`), `src/schema/core.rs:80-84,181-205` (principal `extra` is `EntityRef(MAP_STRINGSTRINGSET)`, `resource.namespace` is a `k8s::Namespace` entity, label maps are entity refs, "Entity ID is user UID, or a random UUID"). The plan fixes only the resource uid (D-11) and says "port `entitybuilder.rs`". A residual keeps entity literals (principal uid in `== principal`, `in`, entity-typed attributes). Phase 2 rebuilds entities from the ACR with different random ids => residual `principal` literal never matches; also `Consistent` requires every partial entity to exist in the concrete store (risk report Q1).
Edit (PLAN 1.3 schema constraints, new bullet + D-12): "D-12 Deterministic entity ids. Every entity that can appear as a literal in a residual has an id that is a pure function of the data: principal id = `uid` if non-empty else `sha256(username)`; `extra`, `groups`, label/annotation maps are **records/sets, not entities** (schema generator change, stage 1 R-9 becomes a hard requirement, not a question); `resource.namespace` is the string `namespace` (D-5). A load-time check rejects schemas with entity-typed attributes reachable from `principal`/`resource` other than the principal and synthetic resource. Existing `new_uuid()` is deleted, not ported." Add to 4 disposition table: `entitybuilder.rs` -> "rewrite; do not port; random ids removed".

### Important

**I1. `Lawful` (C-1) is contradicted by the plan's own fail-closed branches.** Evidence: L3 requires `full a d in PossibleDecisions(conditionsAwareAuthorize a)`; C-6/D-10 return `FailureDecision` for >128 conditions, >10240 bytes, `error` nodes, builder failure. Failing to NoOpinion when `full = Allow` violates L3 and L5 (unconditional must equal `full`). The plan says "soundness is unconditional since failing closed never returns Allow", which is a different property (G2). Edit (PLAN 3.1/3.2): define `Lawful_up_to (H : Attrs -> Prop)` where H = `Fits /\ NoErrorNodes /\ BuilderOk`; state `cedarAuthorizer_lawful` under H and `cedarAuthorizer_guarded_fail_closed` unconditionally (G1/G2 + `result <= full` in the order Allow > NoOpinion > Deny only for Allow). Add a lemma "outside H the result never is Allow".

**I2. K8s constructor rules not mapped (empty map, NoOpinion-only, ID length/charset).** Evidence: kep:1400-1430: zero conditions => NoOpinion **with an error**; >128 => fails closed; ID/type = DNS-1123 subdomain prefix + "/" + name <= 63 chars. PLAN 3.2: IDs `kubernetes.cedarpolicy.com/<policy-id>` with "sanitized to a label-key name part; the encoding and its injectivity are a Lean definition with a lemma". Policy ids from `kubestore.rs` / a CRD are arbitrary strings; an injective encoding into <= 63 chars of `[A-Za-z0-9._-]` does not exist. Collisions give duplicate IDs => the constructor fails closed to Deny for every request of that policy set. Also: if all residuals are dropped (false/error) nothing is conditional and the code must return an unconditional NoOpinion, not call the constructor with zero conditions (error). Edit (PLAN 3.2 Condition encoding): "`id = kubernetes.cedarpolicy.com/p-<first 24 hex of sha256(policy-id)>`; the original policy id goes in `description` (<= 1024 bytes). Lemma: collisions are detected at policy load (reject the policy set), so injectivity is a load-time invariant, not a theorem. The adapter never calls the map constructor with zero Deny and zero Allow conditions; that case returns unconditional NoOpinion (no error)."

**I3. `resource.name` is not "always unknown on create".** Evidence: PLAN 1.3 table. Create on a subresource has the name in the URL (`create serviceaccounts/token`, `pods/binding`, `pods/eviction`: repo comment `src/schema/core.rs` "TIL: Creates can have name from the path already, for subresource requests"; the plan's scope names `create serviceaccounts/token`). Also `object` for these is the request body of a *different kind* (TokenRequest, Eviction, PodExecOptions), `oldObject` null (security.md S-10 "requester-supplied"), so `resource.request` has the subresource's kind and `stored` is `absent`, not the parent's. Edit (PLAN 1.3): "name: `unknown` for create **without subresource** and for deletecollection; `value` for create with subresource. `request` type is the kind of (resource, subresource) in the request's version (e.g. `authentication.k8s.io/v1 TokenRequest`), `stored` is `absent`. Policies cannot see the target object of action subresources (S-10); the schema generator emits no `stored` for them." Add the schema generator work item to stage 1/3.

**I4. Phase-2 data derivation is underspecified (`dataToConcrete`).** The ACR AdmissionRequest provides (kep:2339-2352): uid, kind/resource/subresource (+request* twin fields), name (empty on create), namespace, operation, userInfo {username, uid, groups, extra}, object, oldObject, dryRun, options. Missing from the plan: (a) name on create must come from `object.metadata.name` (generateName already applied before validating admission? the KEP example shows it in `name`; verify against Go and pin it as a test), not `AdmissionRequest.name`; (b) use `requestKind`, not `kind`, or assert both equal (KEP: objects are "in the external version of the request's kind"; a multi-version CRD/HPA is a KEP test, kep:3829); (c) principal type (User/ServiceAccount/Node) is derived from `username` prefix and must be identical to phase 1; (d) `dryRun` and `options` are available but the plan's Cedar context is `{}` (schema `context: {}`); state "not exposed" explicitly; (e) object without apiVersion/kind never reaches the webhook (KEP), so no fallback needed. Edit (PLAN 3.2 `dataToConcrete`): add this list as a normative table "ACR field -> Cedar request/entity field -> phase-1 counterpart".

**I5. The plan misses K8s semantics that change what `full` is.** (1) Update-to-create: secondary `create` check is **unconditional** (`Authorize`) in v1.38 (kep:3219-3232; security.md S-17), so for a Cedar webhook with only conditional create policies, update-to-create requests are denied; document and test (stage 6), not just "out of scope". (2) Re-evaluation: conditions evaluate per object for deletecollection and on every storage retry (P-67, kep:1772-1787); A-4 "served iff full = Allow" must carry the hypotheses single-evaluation or idempotence (purity gives idempotence, state it), and "iff" is wrong in the forward direction because other admission plugins can also reject; say "never served unless". (3) Reload between phases (P-72): the evaluating chain may differ; Cedar's self-contained residuals make the result independent of the store, which is a *selling point*: add as theorem C-8 `store_independent`. (4) Reads before the enforcer (S-5) and unsafe-delete (P-68a) are enforcement-side and belong in the out-of-scope list explicitly.

**I6. Webhook-with-conditions SAR flow: legacy path for writes is not designed.** Per KEP (kep:1860-1900, 3523-3540) the webhook only gets `authorizationOptions` for requests classified conditional (create/update/patch/delete/deletecollection/connect-POST on non-excluded resources) from conditions-aware callers, and any SAR without `handledDecisionTypes` containing ConditionsMap and Union must receive the folded `FailureDecision` (Deny if Deny conditions else NoOpinion). Plan 5c says "legacy `authorize` when no options" but never states that the legacy path for a write runs the same TPE (all-unknown) and folds, nor what it does for reads / non-resource / impersonation / connect GET (all out of scope but still arrive: the webhook is the *cluster's* authorizer). Edit (PLAN 2, Scope): "Out-of-scope request shapes still reach the webhook; they get the unconditional NoOpinion (documented), never an error. Test: every out-of-scope shape returns NoOpinion." Add to 5c: "SAR without options for a write: run TPE, fold with `FailureDecision`."

**I7. Mirror/layout: build specifics.** `lean/mirror/{authorizer,union,webhook,encoding,filters,conditionsenforcer,cel}` are top-level Lake roots in the source package (`lakefile.lean` of kubernetes/lean: `roots := #[`authorizer, ...]`). Vendored under `lean/mirror/` they need `srcDir`/`roots` adjusted or module names become `mirror.authorizer...`; the plan says "unchanged names" but `lib` roots in `lean/lakefile.lean` need a second `lean_lib` with `srcDir := "mirror"`. Also the mirror has 2 axioms (`oAuthor`, `P_76_O3...` in cel/, STATUS.md) and `P_68_enforcer_runs`; plan's axiom audit expects only `propext/Classical.choice/Quot.sound`. Edit (stage 0): "`lean_lib ConditionalAuthz { srcDir := "mirror", roots := ... }`; the audit allows the two named cel axioms and lists them." Cedar-spec modules are `Cedar.*`, so no root-name clash was found.

**I8. Missing stages / deliverables.** (a) Schema generation for writes (resource types per resource+subresource, optional `request`/`stored`, `has`-guard lint, label maps as records, entity-valued attrs removed; `src/schema` is ~2.5k lines and currently emits `k8s::Resource`, `resourceCombined`, `Namespace` entity) has no stage; put it in stage 1 (spike) and stage 3 (generator) explicitly. (b) Policy store (`kubestore.rs` reads policies; CRD or ConfigMap? hot reload? per-policy validation (T-6)) is "rewrite" with no stage. (c) Webhook authn/TLS: the ACR carries full objects (Secrets!); the webhook must require the apiserver's client cert, bind TLS, and `#[instrument(... ret ...)]` in `src/main.rs:193` currently logs return values (and would log objects): add a "no body logging" requirement. (d) Observability (counters for fail-closed branches are promised in D-10 but have no deliverable). (e) Gate-off/version skew is only a stage-6 bullet.

**I9. Existing authorizer cannot be reused as evidence about TPE support of subresource/CRD objects.** Plan relies on the risk report experiments with a 3-entity hand-written schema. No real-object conformance is tested before stage 3 (see Q5).

## Q5: Risk and cheapest early test

Most likely failure: a wrong Attrs<->Data model discovered late (C1, C2, C3, I3, I4 are all instances), and phase-2 conformance of real K8s objects to the generated Cedar schema (Cedar entity validation is strict: unknown or extra attributes, `x-kubernetes-preserve-unknown-fields`, `int-or-string`, quantities, CRDs, version skew all make `entitiesMatchEnvironment` fail, and the plan's C-4 then fails closed => every write to that kind is denied).
Cheapest test (about 1-2 days, in stage 1; add as R-12/R-13):
1. R-12: write `conformance/shapes.json` with ~14 request shapes (create, create+generateName, create subresource token, create pods/exec (CONNECT), update, update->CREATE, patch, patch->CREATE, delete, deletecollection (2 objects), dryRun, multi-version CRD, ServiceAccount principal, node principal), each with the SAR attributes and a captured/hand-built AdmissionRequest (take them from `test/integration/apiserver/conditionalauthorization` in the kubernetes branch). For each, run Rust `PartialRequest`/`PartialEntities` build, TPE with 5 KEP policies, then phase 2 via a plain `Authorizer` over the decoded JSON policies, and compare to `Authorizer` over the original policies with the concrete data. Pass = identical decision for all shapes, and `RequestRefines` accepted. Expect C2 to fail immediately.
2. R-13: take 200 real objects (kind cluster dump of pods, deployments, secrets, configmaps, a CRD with preserve-unknown-fields, a newer-version object) and run them through the schema generator + converter + `validate_entity`. Pass = >= 99% conform; failures listed by cause.
